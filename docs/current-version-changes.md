更新日期：2026-10-20。

本轮工作围绕运行包交付、Eval 基线和图片证据入库展开。图片数据与数据库已通过提交 `495ec22` 合入远端 `main`；本地后续开发位于 `feature/benchmark-v2`。打包工具与本文以当前本地文件为准，不表示所有后续改动都已推送到 `main`。

## 1. ZIP 打包的脚本

### 1.1 解决的问题

直接压缩项目目录容易混入旧 ZIP、下载图片、测试题、日志和备份，也可能遗漏 Chroma 的配套向量文件。因此采用固定白名单，从当前运行目录生成新的 ZIP，并检查文件完整性。

当前提供两个入口：

- [package_submission.py](../package_submission.py)：独立打包脚本，支持正常打包和 `--dry-run` 预检。
- [submission-zip-guide.md](submission-zip-guide.md)：打包规则、每次可直接给助手的指令，以及手动执行方案。

### 1.2 包含和排除的内容

| 内容 | 当前处理方式 |
|---|---|
| `main.py`、`requirements.txt`、`check_setup.py` | 包含，入口直接位于 ZIP 根目录 |
| `bot/` 的 Python 文件 | 包含，用于回答和检索 |
| `build/` 的 Python 和 TXT 文件 | 包含构建工具代码 |
| `.env` | 按用户要求包含在 ZIP 根目录，不输出文件内容 |
| `.venv/` | 按用户要求完整包含，包括依赖、隐藏文件和环境配置 |
| `data/chroma/` | 包含 SQLite 和完整的 `.bin`、`.pickle` 配套文件 |
| `data/text_search.sqlite`、`data/image_search.sqlite` | 包含文字和图片关键词索引 |
| `data/knowledge/` 中的实体、事实和词汇表 JSON | 包含，用于精确事实检索和查询扩展 |
| `data/image_evidence/records.json`、`sources.json` | 包含当前图片证据和来源 |
| 测试题、参考答案、Eval 报告、原图、采集资料、项目缓存、历史 ZIP、备份 | 排除；`.venv/` 内依赖自身的文件完整保留 |

包含 `.env` 的包属于私下交付包，不应公开上传 GitHub。虚拟环境目前对应 Windows / Python 3.13，跨机器使用仍可能需要重建；不能仅凭已打包 `.venv/` 就认定环境可迁移。

### 1.3 运行方式与校验

在项目根目录执行：

```powershell
cd D:\Project\Innowing_Project\ChatbotChallenge2026

# 预检白名单、输入文件和 Git 状态，不生成 ZIP
& .\submission_repo\.venv\Scripts\python.exe .\package_submission.py --dry-run

# 生成并验证新的 ZIP
& .\submission_repo\.venv\Scripts\python.exe .\package_submission.py
```

输出目录为项目旁的 `submission_packages/`。文件名包含时间和 Git 提交号，不覆盖旧包，也不会把生成的 ZIP 再次打包进去。

脚本记录当前工作区文件，因此尚未提交的修改也可能进入包；对应 Git 状态会写入清单。打包过程中不重新采集、描述、生成 embedding 或重建数据库。

脚本的主要检查包括：

1. 必需文件是否存在，Chroma 是否包含向量文件，是否出现未知数据库文件格式。
2. 是否存在需要处理的数据库 WAL、journal 或共享内存文件；检查失败时停止，不能直接删除这些文件绕过检查。
3. ZIP 文件清单是否与白名单一致，`main.py`、`.env`、`.venv/` 是否位于正确位置。
4. ZIP 是否完整，归档内容与打包前后源文件的 SHA-256 是否一致。

包内生成 `PACKAGE_MANIFEST.json`，记录文件清单、大小、哈希、分支、提交号及未提交状态。终端显示 `VERIFIED ZIP` 才表示本次打包校验成功；这不等于 API 连通或回答质量已通过测试。

## 2. Eval 计划的处理方案

### 2.1 当前已完成的基线

已建立 [10 题题集](../submission_repo/eval/curated_test10.json)，包含 5 道本地照片题和 5 道新增图片题。题目绑定参考答案、来源路径和原文证据，先检查参考证据确实存在于当前数据中，再运行检索。

本轮采用以下流程：

1. 使用项目的本地关键词检索，对每题保存前 20 条结果，并计算 Top1、Top5、Top20 的完整证据命中率。
2. 将问题和前 5 条检索证据交给 `gpt-6-luna / low` 作答，作答代理不接触参考答案。
3. 由另一个 `gpt-6-luna / low` 代理依据参考答案和实际提供的证据评分，主代理检查报告中的明显不一致。
4. 分别保留检索结果、实际回答、评分理由和证据引用。

| 当前 10 题结果 | 数值 |
|---|---:|
| 完整正确 | 4 题 |
| 部分正确 | 1 题 |
| 零分 | 5 题 |
| 按 1 / 0.5 / 0 评分后的平均分 | 45% |
| Top1 完整证据命中率 | 20% |
| Top5 完整证据命中率 | 40% |
| Top20 完整证据命中率 | 80% |

6 题回答包含拒答，其中 1 题仍提供了部分正确信息，所以“拒答数量”和“零分数量”并不相同。

完整记录见 [逐题报告](../submission_repo/eval/curated_test10_results/final_report.md) 和 [结构化报告](../submission_repo/eval/curated_test10_results/final_report.json)。主目录同步后已复跑关键词检索，Top5 / Top20 指标保持一致。

**本轮没有调用问题 embedding 或项目聊天 API，也没有执行 `main.py` 的完整回答流程。45% 是本轮“关键词检索 + Luna 作答”的得分，不能视为正式 chatbot 或完整向量混合检索的准确率。** 参考答案来自已有描述，也尚未逐题对照原图核实。

### 2.2 当前发现的问题

- 两道纯中文题没有召回证据，暴露了当前关键词检索在中文问题与英文描述之间的匹配不足。
- 四道题的目标证据位于第 6–20 位，说明相关内容已在库中，但尚未进入提供给回答模型的前 5 条证据。
- 本轮 Luna 作答中，4 道英文问题使用了中文回答，需要单独记录语言遵循情况。
- 现有 10 题样本较小，尚无入库前后的受控对照，不能证明图片处理已经提高了总体 RAG 准确率。

### 2.3 下一阶段拟采用的评估结构

以下是后续 benchmark 的实施计划，不是已经完成的实验结果：

| 层次 | 评估对象 | 重点记录 |
|---|---|---|
| 数据检查 | 题目、答案、证据来源及版本 | 可回答性、来源有效性、原图核验状态、过时或冲突信息 |
| 检索评估 | 关键词检索、真实向量混合检索、可选重排序 | Recall@K、完整证据覆盖、多来源题覆盖、相关结果排名 |
| 回答评估 | 通过真实入口 `main.py` 生成的回答 | 正确性、完整性、无依据断言、合理拒答、语言和耗时 |
| 迭代对照 | 修改前后使用相同数据、题目与评分规则 | 总体及分题型变化、退步案例、运行配置和数据库版本 |

题型计划覆盖一般知识、网页精确事实、图片文字与设备、跨来源聚合，以及本地空间和设施信息。中英文、改写问题及证据不足题应分别统计，避免只报告一个总分。

每道题应保存问题、参考答案或关键事实、来源 URL / 图片 ID、证据原文、核验状态及评分规则。运行结果应保存代码提交、数据或索引哈希、检索配置、模型配置、检索证据、实际回答、错误和耗时，保证之后能复现。

数据划分采用开发集与保留测试集。开发集用于调试，保留集用于阶段性检查；测试题和参考答案不进入知识库，也不放入运行 ZIP。

### 2.4 实施顺序与现有工具

1. 先在当前数据库上，用同一批题比较关键词检索和真实混合检索，定位零召回和排序问题。
2. 再通过 `main.py` 测试回答，区分“没有检索到”和“检索到了但回答错误”。
3. 核查重要题目的原图与原文，扩充题型，并冻结开发集和保留集。
4. 每轮集中改变一个因素，再比较完整指标和失败案例。

目前可使用 [check_images.py](../submission_repo/eval/check_images.py) 的 `lexical`、`hybrid`、`answers` 三种模式，以及 [evaluate_retrieval.py](../submission_repo/eval/evaluate_retrieval.py)。旧文字 benchmark 的框架保留在 `feature/text-benchmark` 分支，后续应按需迁移到当前框架；尚未声称完成统一。

主目录当前开发分支为 `feature/benchmark-v2`。离线基线结果保存在 `submission_repo/eval/image_runs/benchmark-v2-baseline-20261020/`；运行产物与最终交付代码分开保存。

## 3. 图片信息的处理过程

### 3.1 来源、下载和第一轮筛选

图片来源主要包括：

| 来源 | 作用 |
|---|---|
| `image_source/` | 本地拍摄的原始照片 |
| `prompt/` | 按空间组织的本地照片文字描述及原图引用 |
| `prompt_from_web/` | 网页图片清单、来源页面、caption / alt、下载与筛选记录 |

网站清单中的 6,584 条图片 URL 不代表 6,584 张不同图片。同一图片可能有多个 URL、尺寸版本或网页引用，因此先通过脚本下载与缓存，再按原文件 SHA-256 去除完全重复，生成质量和相似性候选。

脚本负责文件校验、下载续跑、尺寸等基础质量信息和相似候选整理。AI 的首轮内容筛选采用 `gpt-6-luna / medium`，并结合人工审阅结果决定保留、暂缓或排除；首轮筛选记录并不表示所有候选都已完成审核。

本轮优先范围冻结为设备 / 设施 165 张、空间布局 230 张，共 395 张。尚未完成的其他图片继续留在各自队列，不混入已完成的数据。

### 3.2 描述生成与 prompt 迭代

已完成的 357 张描述来源如下：

| 描述来源 | 数量 | 版本说明 |
|---|---:|---|
| `gpt-6-luna / low` | 58 张 | `equipment-space-v1`，使用早期简化指令 |
| `gpt-5-mini / low` | 3 张 | `equipment-space-api-v2` |
| `gpt-5-mini / low` | 296 张 | `equipment-space-api-v3` |
| 尚未完成描述 | 38 张 | 因 API 额度限制暂缓 |

API 版本读取 [DESCRIPTION_PROMPT.txt](../prompt_from_web/DESCRIPTION_PROMPT.txt)，覆盖位置、物体与数量、逐字可见文字、空间关系、颜色与材质五类信息，再追加 JSON 输出和设备 / 空间专用规则。旧 Luna 描述没有被追溯标成使用过完整 prompt。

试跑发现关键标签漏识别、遮挡情况下数量不稳、杂项描述过多，因此 v3 增加了关键铭牌和用途标签优先级、文字复查、保守计数，以及降低人物和临时杂物的描述优先级。这些约束改善处理方向，但不代表识别错误已经消失。

[describe_priority_api.py](../submission_repo/build/describe_priority_api.py) 支持逐图保存、断点续跑、跳过有效已有结果和有限重试。每张结果记录原图哈希、描述模型、API 实际返回模型、prompt 版本及哈希、时间和 token 用量，能够区分 Luna 与 GPT-5-mini。

### 3.3 文字层对照、整理和筛选

用户决定先暂停剩余描述，利用已有信息整理可入库证据。本轮处理对象为已完成的 357 张描述：

1. 冻结原始描述、图片哈希、网页上下文，以及原有图片证据快照。
2. 按来源页面 URL 精确关联网页正文，357 张中有 116 张关联到正文；其余仍保留已有 caption、alt 等上下文。
3. 用词项相似度为每张描述提供旧证据比较候选。候选用于检查重复与冲突，不直接证明是同一个设备或空间。
4. 分三批交给 `gpt-6-luna / low` 子代理进行文字筛选，主代理抽查后要求修正部分杂项、数量及模糊判断。
5. 保留内容通过原描述字段和索引引用，避免整理时补写新的规格或地点。

| 筛选结果 | 数量 | 是否进入本次新增检索数据 |
|---|---:|---|
| 保留 | 140 张，导出 140 条片段 | 是 |
| 暂缓、待核查 | 104 张 | 否 |
| 排除 | 113 张 | 否 |

主要排除或暂缓对象包括无关活动场景、临时杂物、不可靠数量、模糊设备判断，以及无法建立相关性的项目或产品照片。原始描述仍保留，便于回查。

图片观察与网页说法保持区分。例如某激光设备网页 caption 写着 Acrylic laser cutting，而此前看图发现标签为 Metal Laser，该项已进入冲突待核查清单，没有自动选择一个说法入库。

**此阶段是文字层筛选，没有对所有图片重新视觉核验。** 新记录标记为 `text_curated_not_visual_verified`。长网页只选择相关上下文检查，也未保证找尽跨视角重复或全部冲突；不能把筛选模型的认可当作视觉事实已被证实。

### 3.4 导出、向量化与入库

[curation/release/](../prompt_from_web/innoacademy/preparation/curation/release/) 提供新增片段、合并片段、来源、逐图决定、待核查项和校验报告。其中：

- `records.json`：本轮新增 140 条片段。
- `merged_records.json`：原有 228 条 + 新增 140 条，共 368 条图片证据。
- `sources.json` / `merged_sources.json`：新增及合并后的来源记录。
- `decisions.json` / `needs_review.json`：筛选理由、原文引用及待核查项。

[ingest_curated_images.py](../submission_repo/build/ingest_curated_images.py) 沿用当前 `text-embedding-3-small`，只为新增片段生成向量。向量按批缓存，全部准备好后再追加写入 Chroma，并同步图片 BM25、`records.json` 和 `sources.json`。中断后可复用缓存继续处理，旧文字与图片向量保留。

这里向量化的是**图片的文字描述**，没有直接生成图片像素的多模态向量。当前入库回执 [curated_indexed.json](../submission_repo/data/image_evidence/curated_indexed.json) 已记录 `status=complete`。

当前 368 条图片证据中，`prompt/` 的 28 份描述文档全部覆盖，对应 119 张本地原图和 168 条检索片段；其余 200 条为网站图片相关证据。图片数、描述文档数和检索片段数是不同统计单位。

描述阶段的 `summary.json` 仍可能显示 `indexed=false`，它记录的是该描述批次的阶段状态，不能代替后续整理入库回执。判断是否已经入库，应结合最终回执和当前检索数据。
